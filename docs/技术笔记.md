# 技术笔记

记录实现过程中踩到的坑，方便后来者（也包括半年后的自己）。

## 1. TR2013 的档案结构

- `bigfile.000-003.tiger`、`patch.000.tiger`、`patch2.000.tiger`、`title.000.tiger`、`jcontent.000.tiger`
  是资源包；`_ENGLISH` / `_JAPANESE` 后缀的是语言包（含语音，约 1 GB）。
- 文本文件内部路径：`pc-w\local\locals.bin`。
- 同一个 `locals.bin` 在包里存在 14 份，靠 `locale` 字段区分（`en`、`zhhant`、`ja`…）。
- 档案优先级按 id 升序，后加载覆盖先加载：`bigfile(0) < patch(65) < jcontent(66) < patch2(67)`，
  mod 档案排最后，所以 `patch2` 是 TR2013 的「最终覆盖层」。

## 2. locals.bin 二进制格式（TR2013）

```
int32  languageId
int32  numInputSpecificStringIds
int32  numStrings
int32[numInputSpecificStringIds]  inputSpecificKeys
int32[numStrings]                 stringPositions   // 指向字符串的偏移，0 表示该键没有文本
...                               utf8 字符串（\0 结尾）
```

`TrRebootModTools` 把它读成 `Dictionary<string,string>`（键就是序号），转 JSON 后便于编辑。

## 3. 坑一：mod 里 locals.bin 的目录结构

mod 目录中，`locals.bin` 是**目录名**，文件名是语言代码：

```
mod\
└─ pc-w\
   └─ local\
      └─ locals.bin\        ← 目录
         └─ zhhant.json     ← 文件名 = 语言代码
```

原因在 `FolderModPackage.AddFilesAndResourcesFromFolder`：它先用
`LanguageCodeToLocale(Path.GetFileNameWithoutExtension(file))` 从**文件名**解析语言，
解析成功后再把文件名去掉，剩下的路径拿去算哈希。所以：

- `pc-w\local\locals.bin\zhhant.json` → 哈希 `pc-w\local\locals.bin` + locale `zhhant` ✅
- `pc-w\local\locals.json` → 哈希 `pc-w\local\locals.json`（游戏里不存在），locale 无法解析 ❌
  会静默写入一个「新文件」，不报错也没效果。

## 4. 坑二：上游写入 bug（已修复）

`Shared/Cdc/Tr2013/Tr2013LocalsBin.cs` 写指针时：

```csharp
stream.Position = stringPositionsPos + PointerSize * i;
writer.Write(stream.Length);   // Length 是 long → 写 8 字节
```

指针槽只有 4 字节，于是每次写指针都会把**下一个**槽位的低 4 字节清零；循环继续会修正，
但**最后一个**指针写完后多出的 4 字节落在第一条字符串的起始处，把它清零。

由于这份文本没有 key `0`，第一条字符串就是 key `1`——菜单第一项「開始遊戲」变成空白。

修复：

```csharp
if (PointerSize == 4)
    writer.Write((int)stream.Length);
else
    writer.Write(stream.Length);
```

补丁见 `patches/0001-tr2013-localsbin-pointer-size.patch`。

## 5. 坑三：验证时读错了档案

`ArchiveSet` 会把 `bigfile._orig.patch2.000.tiger`（打补丁时的官方备份）当作基准数据加载，
并**跳过**真正的 `patch2.000.tiger`：

```csharp
if (GetAllFlattenedModArchiveIdentities().Any(i => i.FileName == archiveFileName))
    return false;
```

所以用 `ArchiveSet` 去读只会看到原文，误以为补丁没生效。要校验必须直接用
`Archive.Open("patch2.000.tiger")`——这就是 `TrTextTool inspect` 存在的原因。

## 6. 为什么必须改 zhhant 槽位

字库是分语言的资源集合（`pc-w\fontchinese.drm`、`fontjapanese.drm`、`fontuniversal.drm`…），
游戏按当前语言加载。把中文写进 `en` 槽位，游戏仍用拉丁字库渲染，结果是方块或缺字。
所以补丁只动 `zhhant`，界面/字幕会以简体显示，但字体链路仍是中文那一套。

实测确认：安装后主菜单显示「开始游戏 / 选项 / 技术支援 / 结束游戏」，
设置页显示「基本 / 进阶 / 全屏 / 分辨率 / 垂直同步 / 质量」，无缺字。

## 7. 繁转简的两个细节

- **按钮图标**：原文里有 179 条字符串内嵌私有区字符（U+E000–U+F8FF），
  形如 `<font color="#FFFFFF">\ue009</font>`，代表手柄按键图标。
  JSON 往返和 OpenCC 都不会动它们，但替换规则如果用了贪婪正则就有风险，
  所以脚本里只做纯字符串替换，并在结尾自检图标数量。
- **台湾用语**：OpenCC 只做字形转换，`滑鼠` 会变成 `滑鼠`（不是「鼠标」），
  `檔案` 变成 `档案`（不是「文件」）。所以需要先用词表替换，再跑 OpenCC。
  句式类（「進行遊戲」→「运行游戏」）要放在 OpenCC 之后，因为要匹配简体字。

## 8. 构建环境

- 上游代码使用 C# 14（`/langversion:14`），需要 **.NET SDK 10**；用 SDK 8 会报
  `CS1617: /langversion 的选项"14"无效`。
- `TrTextTool` 的目标框架是 net8.0 也能编译，但必须用 SDK 10 的编译器。
- 不要开 `InvariantGlobalization`：`Tr2013ArchiveSet` 静态构造函数里调用了
  `CultureInfo.GetCultureInfo(1041)`，在不变模式下会抛异常。
- PowerShell 5.1 读取无 BOM 的 UTF-8 脚本会按 GBK 解析导致语法错误，
  所以 `build.ps1` 保存为 **UTF-8 with BOM**。

## 9. 致命问题：游戏 UI 字库只含繁体字形

**现象**：安装简体文本后，主菜单变成「新游□」「□束游□」「多人口机游□」，
HUD 与字幕也大量方框。

**验证**：把菜单项替换成繁体/简体对照串再截图，结果非常干净：

| 显示 | 字符 |
|---|---|
| 正常 | 戲 結 聯 別 錄 繼 續 畫 開 |
| 方框 | 戏 结 联 别 录 继 续 画 开 |

即：**同一位置，繁体形能渲染，简体形是方框**。字形不存在，与文本编码无关。

**量化**：

- 简体文本 40494 个汉字中，12616 个（31.2%）不在官方繁体文本的字符集里；
- 3388 条字符串中 2846 条（84%）至少含一个这种字。

**字体资源**：`pc-wontchinese.drm` 里有个 4.4 MB 的 `.tr9dtp`，头部是 `GFX` 魔数、
尾部是 `pixelFont` 标记，内容是 Scaleform 位图字体（约 2048×2048 的图集 +
206 KB 的度量表，名为 `fonts_zh_all`）。`fontarabic / fontjapanese / fontkorean /
fontrussian / fontuniversal` 是同族资源，全部只有一个 CJK 图集。

**容易误判的地方**：

- 标题界面（开始游戏 / 选项 / 技术支援 / 结束游戏）和启动前的设置窗口显示简体**正常**，
  因为它们走 GDI/系统字体（DirectWrite），不读游戏字库；先前的验收截图正是这两个界面，
  因此漏掉了问题。真正的验收必须进入**主菜单 / 存档界面 / 游戏内 HUD / 字幕**。
- 即便把文本写进 `en` 槽位也一样：用的是同一套位图字库，方框照样出现。

**结论**：这款游戏的汉化必须**替换或重建字体资源**，纯文本补丁不可能完整。
社区成熟方案（如 intergra/TR2013-Simplified-Chinese）都用 Noto Sans SC 重建了字库。
若要自己做，工作量为：解析 GFX pixelFont 的图集与度量表 → 用 TTF 重新光栅化
所需字符集 → 回写图集与表。属于独立的字体工程，不在纯文本补丁范围内。

## 10. 社区汉化包的结构与 Mod Manager 版本问题

### 包结构

`TR2013-Simplified-Chinese.zip`（v8.0，约 1.1 GB，3628 个条目）：

```
licenses/                     Noto Sans SC / KR 的 OFL 与版权声明
local/localization/movies/*.sch   外部影片字幕
pc-w/local/locals.bin/zhhant.json  简体中文文本（约 180 KB）
pc-w/fontchinese.drm/Dtp/24824.tr9dtp   重建的中文字库（18.3 MB）
pc-w/global_menus.drm/Dtp/29628.tr9dtp  菜单布局调整
pc-w/cinstream/*.mul + *.ips32     实时过场字幕
pc-w/audio/streams/vo/**/*.mul + *.ips32  对话字幕
```

字体资源的替换方式是**替换集合内的资源**：路径 `pc-w\<集合名>.drm\Dtp\<资源 id>.tr9dtp`，
其中资源 id 用十六进制文件名表示（原字体是 `0x60F8` = 24824）。
新字库 18.3 MB vs 官方 4.4 MB —— 官方那张图集只画了繁体字。

注意 mod 里 `locals.bin` 是**目录名**（语言代码作文件名），与第 3 节讲的一致。

### Mod Manager 版本

社区要求使用 Nexus 上的 **Mod Manager 1.10.0**，并明确警告不要用 1.11.0。

但 GitHub 上游仓库（arcusmaximus/TrRebootModTools）的版本号与 Nexus 的发行版并不是
同一套代码：

| 版本 | 来源 | 对 TR2013 资源替换的表现 |
|---|---|---|
| 1.10.0（提交 `5309f18`） | GitHub 源码 | **崩溃**：`EndOfStreamException` |
| 1.11.0（HEAD） | GitHub 源码 | 安装成功，游戏内显示正常 |

1.10.0 崩在 `ModInstaller.CollectExternalResourceKeys` → `ResourceRefDefinitions.Create`：
它在资源流当前位置读 `RefCounts`，而 TR2013 的 `.tr9dtp` 资源前面带 12 字节
`GFX` 文件头（`u32 size` + `"GFX"` + `u32 size`），
直接按位置读会读到文件大小当引用计数，于是越界。

实测对照：用同一个解析器读**官方字体文件**和 **mod 提供的字体文件**，两者都抛同样的异常
—— 说明这是工具侧的解析问题，不是 mod 文件坏了。

1.11.0 重写了资源读写（`Shared/Serialization/ResourceReader` 与 `ResourceBuilder`，
删除了旧的 `ResourceRefDefinitions`），不再踩这个坑，因此能正常安装。

### 本仓库脚本的做法

`scripts/install-community-mod.ps1` 用 1.11.0 源码构建的命令行方式完成安装，
并已实测：主菜单为完整简体中文，无方框。

社区关于 1.11.0「CG 卡死 / 文献无声 / 返回主菜单异常」的提醒仍然有效，
若遇到这些现象，请改用 Nexus 的 1.10.0 GUI 工具安装。

## 11. 验收方法（重要）

不要只看启动前的标题界面和设置窗口 —— 那些走 GDI / DirectWrite 系统字体，
中文永远显示正常。**必须进入主菜单、存档界面、游戏内 HUD 和字幕**，
这些用的是游戏自己的位图字库，才是验收点。

本仓库最初的「补丁成功」结论就是只看了标题界面得出的，是误判。
